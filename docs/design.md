# AgentPitch — Design & Architecture

This document describes the design principles, layer boundaries, and data flows that make up the AgentPitch simulation engine.

---

## Overview

AgentPitch is an LLM-powered soccer simulation where every player on the field is an AI agent. Each player's `decide()` callback is generated by a large language model, executed inside a language-specific sandbox, and evolved automatically after every match based on the recorded match log. Strategies can be written in Python, JavaScript, or Rust.

The system has four layers:

```
┌─────────────────────────────────────────────────────┐
│  API  (FastAPI HTTP server + React browser UI)       │
├─────────────────────────────────────────────────────┤
│  Orchestration  (TickEngine, CLI runners)            │
├─────────────────────────────────────────────────────┤
│  Core  (GameStateManager, movement & physics)        │
├─────────────────────────────────────────────────────┤
│  Foundation  (PAL, sandboxes, CGP, PMEP, actions)   │
└─────────────────────────────────────────────────────┘
```

**Hard boundary:** The API layer must not import from `src/foundation/`. API-layer Pydantic models in `src/api/http_server/` mirror `src/foundation/config_models.py` independently. The only cross-layer exceptions are `src/secrets_store.py` and `src/strategy_library.py` — pure file I/O with no engine code.

---

## Layers

### Foundation (`src/foundation/`)

The lowest-level abstractions shared by every other layer.

| Module | Responsibility |
|--------|---------------|
| `action.py` | Immutable frozen dataclasses: `Action`, `Move`, `Pass`, `Shoot`, `Tackle`, `Hold`. `Action.from_tagged()` normalises return values from JS/Rust sandboxes. |
| `decide_contract.py` | Signature verification for `decide(game_state, player_state, history)` and reference invocation harness. Deep-copies all arguments before passing them to the callback. |
| `game_state_schema.py` | `GameStateDict` TypedDict + runtime validator. Player IDs are always strings in the format `"{team_id}_{index}"`. |
| `config_models.py` | Pydantic v2 `MatchConfig`: frozen, strictly validated, shared across core/orchestration. |
| `provider_abstraction/` | **PAL** — single async `generate()` entry point for all LLM calls. Adapter registry for OpenAI, Anthropic, Gemini, plus an `openai_compatible` type for custom endpoints. Lazy per-`(provider, api_key)` cache and retry/backoff logic. |
| `sandbox/` | `SandboxFactory` dispatches `.py` → `RestrictedPythonSandbox`, `.js` → `QuickJSSandbox`, `.rs` → `WasmtimeSandbox`. Backends for JS and Rust are optional extras, lazy-loaded on first use. |
| `code_generation_pipeline/` | **CGP** — builds a Jinja2 generation prompt, calls PAL, extracts `decide()` code, compiles it in a sandbox, and persists the strategy file. Up to 3 retries; on compile failure the error is fed back into the next prompt. |
| `post_match_evolution_pipeline/` | **PMEP** — reads the prior strategy and match summary, builds a Jinja2 evolution prompt, calls PAL, compiles the result, and writes the new strategy. Falls back to generation if no prior strategy exists. |
| `system_prompt_builder/` | Jinja2 templates for generation and evolution prompts. Separate template sets for Python, JavaScript, and Rust. |
| `action_resolution_engine/` | 7-phase per-tick orchestrator (see [Tick loop](#tick-loop)). Stateless — tick-local state is re-initialised on every call. |

### Core (`src/core/`)

The stateful game simulation engine.

| Module | Responsibility |
|--------|---------------|
| `game_state_manager.py` | Single source of truth for all match state (player positions, ball, score, phase, cooldowns). Builds the per-tick snapshot passed to every `decide()` call. Deterministic kickoff via hash of a seed. |
| `player_movement_system.py` | Stateless functions that apply validated `Move` actions to player positions using snap/discipline soft-anchoring. Calibrated to ≈10 m/s maximum speed. |
| `ball_physics_system.py` | Stateless functions that handle ball motion, control contests, pass/shoot resolution, and tackle interactions. |
| `match_log_system.py` | Records a `TickRecord` + `ActionRecord` per player per tick. Implements a `LIVE → FINALIZED` state machine; prevents double-finalization. Selects up to 5 key events (goals, fallbacks, tackles, shots, interceptions) with recency bias for the evolution prompt. |

### Orchestration (`src/orchestration/`)

Match execution and tournament coordination.

| Module | Responsibility |
|--------|---------------|
| `tick_engine/engine.py` | Composition root. Constructs all 7 subsystems, compiles strategies for both teams, runs the main tick loop, handles phase transitions (GOAL_SCORED pause, HALF_TIME, FULL_TIME), and triggers PMEP when the match ends. |
| `action_resolution_engine/engine.py` | Coordinates the 7 tick phases: snapshot → action generation → validation → movement → ball actions → tackle resolution → ball physics + goal detection. |
| `cli/` | `season_runner.py`, `cup_runner.py`, `league_runner.py` — async orchestrators that schedule matches, call CGP/PMEP, and write tournament metadata to disk. |

### API (`src/api/http_server/`)

FastAPI HTTP server on port 8765 with a React browser UI.

- Accepts match/tournament creation requests, validates them against its own independent Pydantic models, and spawns CLI subprocesses for long-running work (strategy generation, cup/league runs).
- Serves live match events over SSE for the browser viewer.
- Reads strategy library and match output files directly from disk.

## Tick loop

The 7-phase tick structure ensures all player decisions are based on the same snapshot and that physics mutations happen in a deterministic order:

| Phase | Action |
|-------|--------|
| 1 | Collect per-player snapshots (`game_state`, `player_state`, `history`) |
| 2 | Execute `decide()` in sandbox (5 ms budget; failure → `Hold`) |
| 3 | Validate actions (range checks, cooldown enforcement) |
| 4 | Apply player movement (`PlayerMovementSystem`) |
| 5 | Resolve pass/shoot ball actions (`BallPhysicsSystem`) |
| 6 | Resolve tackles |
| 7 | Apply ball physics + detect goals |

All phases read from the Phase 1 snapshot, so no player can observe another player's action in the same tick.

**Cooldown:** A single per-player cooldown timer is triggered by `Pass`, `Shoot`, `Tackle`, and `Pickup`. While a cooldown is active the player can only `Move` or `Hold`. `Move` and `Hold` never trigger a cooldown.

## Sandbox system

Every player's `decide()` callback runs inside a language-specific sandbox that enforces a strict execution budget and restricts what the code can access. The sandbox system is defined by the `Sandbox` Protocol and implemented in `src/foundation/sandbox/`.

### Dispatch

```
SandboxFactory.for_strategy_path(suffix)
  .py  →  RestrictedPythonSandbox   (always available)
  .js  →  QuickJSSandbox            (requires pip install -e '.[js]')
  .rs  →  WasmtimeSandbox           (requires pip install -e '.[wasm]')
```

All three implementations satisfy the same `Sandbox` Protocol:

```python
def compile(player_id: str, source: str) -> SandboxResult   # once per match
def execute(player_id, game_state, player_state, history) -> SandboxResult  # every tick
def disable(player_id: str) -> None                          # circuit breaker
```

### SandboxResult

Every call to `compile()` or `execute()` returns a `SandboxResult`:

```python
@dataclass
class SandboxResult:
    status: ExecutionStatus
    action: Optional[Action] = None
    serialization_ms: float = 0.0   # data-prep cost (deepcopy / json / msgpack)
    execution_time_ms: float = 0.0  # runtime cost (fn call / eval / wasm)
    error_type: Optional[str] = None
    error_message: Optional[str] = None
```

`serialization_ms + execution_time_ms` is the total cost of one `execute()` call, comparable across all three sandbox types. `error_type` carries only the exception class name — no tracebacks or implementation details.

`ExecutionStatus` values:

| Status | Meaning |
|--------|---------|
| `SUCCESS` | Valid `Action` returned |
| `COMPILE_ERROR` | Source failed AST compile or module-body execution |
| `TIMEOUT` | Exceeded 5 ms wall-clock budget |
| `EXCEPTION` | Callback raised an exception |
| `INVALID_RETURN` | Callback returned a non-`Action` value (or generator/coroutine) |
| `DISABLED` | Circuit breaker tripped; returns `Hold()` without calling the code |

Non-`SUCCESS` results are forwarded to `FallbackHandler`, which returns `Hold()` and records a `FallbackEvent` in the match log. The circuit breaker fires after 10 consecutive timeouts and suppresses further invocations for the rest of the match.

### Per-player state

Each sandbox keeps a `_contexts` dict keyed by `player_id`. For Python this is `PlayerSandboxContext` (holds `compiled_fn`, `module_globals`, timeout counter, and disabled flag). JavaScript uses `_QuickJSPlayerContext` (holds a `quickjs.Context`). Rust uses `_WasmPlayerContext` (holds a `wasmtime.Store`, `Instance`, and memory handle). A fresh context is installed on every `compile()` call — recompile always replaces prior state.

### Python sandbox (RestrictedPython)

**Source:** `src/foundation/sandbox/python_sandbox.py`

`compile()` runs in two steps:

1. **AST compile** via `compile_restricted()` (Zope RestrictedPython) — rewrites attribute access, subscript, and iteration to use guard hooks so the restricted globals dict controls what the code can touch.
2. **Module-body exec** in the restricted namespace — runs module-level code (imports, class definitions, helper functions) at compile time.

If a callable `decide` symbol is not found after both steps, the result is `COMPILE_ERROR`.

`execute()` procedure:

1. **Deep-copy** `game_state`, `player_state`, and `history` before arming the timer (copy cost is measured separately as `serialization_ms`).
2. **Arm timer** — `signal.setitimer(ITIMER_REAL, 5 ms)` pointing at `_timeout_handler`.
3. **Call** `compiled_fn(gs_copy, ps_copy, h_copy)`.
4. **Disarm timer** immediately in the `finally` block and restore the prior `SIGALRM` handler.
5. **Validate return** — must be an `Action` instance that is not a generator or coroutine.

**Timeout sentinel:** `_SandboxTimeoutError` subclasses `BaseException`, not `Exception`, so an LLM-generated `except Exception` block cannot swallow it. A second safety net catches any `_SandboxTimeoutError` that fires inside an exception handler before the `setitimer(0)` call executes.

**Restricted namespace** (`src/foundation/sandbox/namespace.py`): the `module_globals` dict exposes:

- **6 Action classes** — `Action`, `Move`, `Pass`, `Shoot`, `Tackle`, `Hold` — available without import.
- **28 safe builtins** — numeric (`abs`, `max`, `min`, …), sequence (`len`, `range`, `sorted`, `zip`, …), type constructors (`int`, `str`, `list`, `dict`, …), and `isinstance`. Notably absent: `__import__`, `exec`, `eval`, `compile`, `open`, `print`, `getattr`, `setattr`, `globals`, `locals`.
- **5 RestrictedPython guards** — `_getitem_`, `_getattr_`, `_getiter_`, `_write_`, `_inplacevar_` — required for any dict/list access or augmented assignment to work at all.
- Augmented assignment (`+=`, `-=`, `*=`, `/=`) is allowed; bitwise and shift variants are blocked.

A fresh namespace dict is constructed for each player so cross-player state cannot leak.

### JavaScript sandbox (QuickJS)

**Source:** `src/foundation/sandbox/quickjs_sandbox.py`

Uses the `quickjs` PyPI binding. Each player gets a dedicated `quickjs.Context` (V8-style isolate — no shared heap).

`compile()` evaluates a security prelude first:

```javascript
globalThis.Date = undefined;
globalThis.setTimeout = undefined;
globalThis.setInterval = undefined;
globalThis.console = undefined;
globalThis.eval = function(){ throw new Error("eval blocked"); };
globalThis.Function = function(){ throw new Error("Function blocked"); };
Object.freeze(globalThis.Math);
```

Then evaluates the user source and verifies `typeof decide === 'function'`.

`execute()` procedure:

1. **Set time limit** — `ctx.set_time_limit(5 ms)`.
2. **Serialise** arguments to a JSON string (`serialization_ms`).
3. **Eval** `JSON.stringify(decide.apply(null, <args_json>))` inside the context.
4. **Parse** the returned JSON string and call `Action.from_tagged(tagged)` to normalise the JS object dict into a Python `Action` subclass.

Timeout is detected by checking for `"interrupted"` in the `quickjs.JSException` message. The circuit breaker increments on each timeout and disables the player after 10 consecutive occurrences.

Cross-tick persistent state is supported: variables defined in the JS module body survive across `execute()` calls because the same `quickjs.Context` is reused.

### Rust / WASM sandbox (Wasmtime)

**Source:** `src/foundation/sandbox/wasm_sandbox.py`

Rust strategies are compiled to `wasm32-wasip1` WebAssembly via `cargo` at match start (result cached by `sha256(source)` under `~/.cache/agent-pitch/wasm/`). The compiled `.wasm` binary is then instantiated once per player using the `wasmtime` Python binding.

**Process-wide singletons:** a single `wasmtime.Engine` (with `epoch_interruption = True`) and a daemon thread (`wasmtime-epoch-ticker`) that calls `engine.increment_epoch()` every 1 ms. This gives ~1 ms timeout granularity via `store.set_epoch_deadline(n)` armed before each `decide()` call.

**Per-player isolation:** each player gets its own `wasmtime.Store` and `Instance` with independent linear memory. No memory is shared across players.

**WASI capability:** `linker.define_wasi()` with a restrictive `WasiConfig` (no inherit, no preopen) provides the 4 standard WASI helpers (`environ_get`, `environ_sizes_get`, `fd_write`, `proc_exit`) needed by the Rust standard library, but grants zero filesystem, network, clock, or environment access.

**Deterministic randomness:** a `host.random_u64` host function backed by splitmix64 is injected. The seed is derived from the sandbox seed XOR the player ID hash, making randomness reproducible per player across identical runs.

**Required exports** from the user's Rust strategy:

| Export | Signature | Purpose |
|--------|-----------|---------|
| `alloc_buf(len) → ptr` | `i32 → i32` | Allocate input buffer in wasm memory |
| `dealloc_buf(ptr, len)` | `i32, i32 → ()` | Free buffer |
| `decide(ptr, len) → status` | `i32, i32 → i32` | Execute decide logic; 0 = success |
| `return_ptr() → ptr` | `() → i32` | Pointer to output buffer |
| `return_len() → len` | `() → i32` | Length of output buffer |

`execute()` procedure:

1. **Serialise** `(game_state, player_state, history)` to MessagePack (`serialization_ms`).
2. **Arm epoch deadline** — `store.set_epoch_deadline(timeout_ms)`.
3. **Alloc** input buffer via `alloc_buf`, write payload into wasm linear memory.
4. **Call** `decide(ptr, len)` — raises `wasmtime.Trap` on timeout or memory fault.
5. **Read** output bytes via `return_ptr` / `return_len`, then dealloc both buffers.
6. **Decode** MessagePack output and call `Action.from_tagged()`.

Timeout is detected by `"epoch"` or `"interrupt"` in the `wasmtime.Trap` message, triggering the same circuit breaker as the other sandboxes.

> **macOS note:** Wasmtime's Cranelift JIT writes RWX pages. Apple-shipped Python (Xcode CLT) runs under Hardened Runtime without the `com.apple.security.cs.allow-jit` entitlement, which causes the kernel to SIGKILL the process on first wasm execution. Use Homebrew, python.org, or pyenv-built Python.

### Mixed-language matches

Because the sandbox is selected per strategy file extension, team A and team B can run entirely different languages in the same match — e.g. a Python strategy versus a Rust strategy. The `TickEngine` constructs one `Sandbox` instance per team and calls `compile()` / `execute()` through the shared protocol, so the rest of the engine is language-agnostic.

## Provider Abstraction Layer (PAL)

```python
async def generate(
    prompt: str,
    team_id: str,
    config: MatchConfig,
    *,
    provider_type: str | None = None,
    base_url: str | None = None,
) → LLMResponse
```

Constants: temperature `1.0`, max tokens `8192`, up to 3 retry attempts with exponential backoff (1 s, 2 s).

**Adapter registry:**

| Key | Adapter | Notes |
|-----|---------|-------|
| `openai` | `OpenAIAdapter` | Standard OpenAI API |
| `anthropic` | `AnthropicAdapter` | Anthropic API |
| `gemini` | `GeminiAdapter` | Google Gemini |
| `openai_compatible` | `OpenAIAdapter` | Custom `base_url` (DeepSeek, OpenRouter, Ollama, …) |

Adapters are cached lazily per `(provider, api_key)` tuple. Retriable errors (429, 5xx, connection/timeout) trigger the backoff loop; non-retriable errors (401, 403, 404, 400) fail immediately.

LLM provider and model settings are stored outside `MatchConfig` in `<DATA_HOME>/llm-providers.yaml` and `.secrets.json`, so they can be changed from the Config UI without affecting saved match configurations.

## Strategy lifecycle

A strategy is a plain source file (`.py`, `.js`, or `.rs`) containing a `decide()` function. The file is prefixed with a metadata comment block when written:

```
# Provider: anthropic
# Model: claude-opus-4-7
# Generated_by: code-generation-pipeline
# Language: python
# Version: 1
```

Strategies live in `data/strategies/` (current, evolving versions) and `data/library/` (user-saved snapshots). The Tick Engine parses the header for display in the browser UI.

At the start of every match the CGP generates a fresh strategy (or the UI provides one explicitly). At the end PMEP reads the prior strategy and the match summary, and writes an evolved version back to disk. Strategies thus improve iteratively across a season.

## Key design decisions

### Player ID convention

All player IDs are strings of the form `"{team_id}_{index}"` (e.g. `"team_a_0"`, `"team_b_3"`). Never integers. This is enforced by the `GameStateDict` runtime validator and checked in tests.

### API layer boundary

The `src/api/` layer must not import from `src/foundation/`. Pydantic models are duplicated independently. This prevents HTTP validation logic from coupling to engine internals and allows the API models to evolve independently (e.g. versioning, extra UI fields).

### 7-phase tick orchestration

All 7 phases read from a single snapshot built at Phase 1. This makes the tick deterministic: no player can observe a sibling's action in the same tick, and physics mutations happen in a fixed, predictable order.

### Unified cooldown

A single cooldown timer per player (ticks) replaces earlier piecemeal cooldown rules. It is triggered only by `Pass`, `Shoot`, `Tackle`, and `Pickup`. `Move` and `Hold` are always available. This simplifies strategy authoring and prevents degenerate pass-immediately-recollect patterns.

### External LLM settings

Provider and model are not stored in `MatchConfig`. They live in `llm-providers.yaml` and `.secrets.json`, managed by the Config UI. This means a saved match config is reproducible regardless of which LLM is currently configured, and the LLM can be swapped without touching any match or tournament definition.

### SandboxFactory dispatch

The sandbox backend is chosen purely by file extension. Mixed-language matches work out of the box: team A can use a Python strategy while team B uses JavaScript or Rust. Optional backends are loaded lazily so the base install (Python-only) remains lightweight.

## Testing

```
tests/
├── unit/          # fast, no I/O, no LLM calls
├── integration/   # may touch filesystem
└── performance/   # benchmark smoke tests
```

`conftest.py` provides shared fixtures (`all_player_ids`, `team_a_ids`, `team_b_ids`). `_reset_adapter_cache()` is available as a test helper to clear the PAL adapter cache between cases. The sandbox circuit breaker state can be reset per-test by constructing a fresh `RestrictedPythonSandbox` instance.

Run the full suite with `make test`; coverage (≥ 80% required) with `make test-cov`.
